# N1 模組資產盤點與整合契約

N1 現有資料不應被視為空白環境。每一項新部署，包括語音、記憶、研究、編碼、交易與設備維護能力，都必須先以唯讀巡檢辨識既有資產，再決定是否沿用、補完、合併、新建或交由主人確認。

| 分類 | 可接受證據 | 預設部署決策 |
|---|---|---|
| 已運作 | PM2、Docker 或 systemd 顯示該服務存在且有狀態 | 沿用；先確認健康檢查與公開契約。 |
| 已安裝未接線 | 已知套件、模型或服務原始碼存在，但沒有受管理程序 | 補完；優先補 API、服務註冊或啟動設定。 |
| 半完成 | 安裝器、路由、資料夾或部署檔存在，卻缺少可驗證的完整啟動鏈 | 人工確認或補完；不得直接覆寫。 |
| 重複候選 | 同名腳本或來源檔出現於多個位置 | 人工比較用途、入口點、相依套件與實際呼叫點；同名不等同重複。 |
| 未知 | 僅有路徑／檔名，沒有服務、套件或呼叫證據 | 保持不動並等待分類。 |

> 巡檢只列出服務名稱、狀態、套件名稱、模型名稱與允許副檔名的檔案路徑。它不讀取 `.env`、憑證、API 金鑰、聊天／記憶內容、任意設定檔內容或原始音訊內容。

## 部署門檻

| 決策 | 條件 | 後續動作 |
|---|---|---|
| 沿用 | 現有模組有清楚健康檢查與契約 | App 先串接現有 API。 |
| 補完 | 有有效基礎但缺路由、背景程序或報告 | 提供最小可回復補丁與驗證命令。 |
| 合併 | 已確認兩個模組功能重疊且有明確保留目標 | 先備份，再分階段遷移與驗證。 |
| 新建 | 沒有可用基礎或現有方案不符需求 | 先提出架構與部署計畫，經確認後安裝。 |
| 人工確認 | 來源、用途或副作用不清楚 | 預設阻擋覆寫、重啟與啟動。 |

## 與艾西的關係

艾西可在記憶中心顯示這些分類與建議，但只有 N1 回傳的可驗證盤點結果可標為「已發現」或「可用」。艾西不得把檔名、對話推測或舊文件當成模組已安裝、已啟動或可執行的證據。
