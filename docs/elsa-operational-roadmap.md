# ELSA 長期運行能力藍圖

## 結論

ELSA 的**控制台骨架與可觀測性基礎已完成**：App 已能在記憶中心顯示 N1 永動腦、資源、策略、服務端記憶、三機結構快照與未回報狀態；N1 亦已有任務佇列、資源、結構、保護與記憶同步的受控回報路由。現在最缺的不是再增加一個聊天頁或模型，而是把「發現能力」變成「可驗證使用能力」的閉環。

> **ELSA 的下一個核心里程碑：** 模組能被盤點、提出部署方案、經核准部署、經健康檢查驗證、被艾西與 App 真實使用，並在失敗時可回復。

## 現有能力與真實狀態

| 領域 | 目前狀態 | 真實證據／限制 | 下一步 |
| --- | --- | --- | --- |
| N1 與三機觀測 | 已接入 | 永動腦、資源與結構資料均以 N1 回報或明確手動快照顯示 | 補齊 inventory 的真實連線、服務版本與最後驗證資料 |
| 永動腦任務 | 已有契約與佇列 | 任務、取消與部署核准路由存在；聊天回答不可當作執行證據 | 讓工作者真正消費任務、回傳測試、Git、部署與失敗摘要 |
| 模組資產盤點 | 已有唯讀腳本 | 可分類服務、來源、套件、模型、安裝器與文件；不讀取秘密值 | 將報告保存為結構化 JSON，供艾西與 App 查詢 |
| 受控部署 | 尚未形成閉環 | 已有沿用／補完／合併／新建的決策原則 | 建立白名單部署方案、備份、核准、驗證與回滾記錄 |
| 長對話記憶 | 尚在設計 | 本機聊天可保存；尚不能證明新視窗已讀取 N1 索引文件 | 實作分段文件、摘要、N1 匯入、索引與相關脈絡提取 |
| N1／R2 記憶分層 | 回報路由已就緒 | 目前可能回傳 `unreported`，代表同步工作者尚未提供真實資料 | 實作去重、摘要、向量索引、R2 原檔封存與錯誤重試工作者 |
| 語音 | 試聽與裝置朗讀可用 | 影片音軌只可試聽；尚無可合成任意新句子的固定角色聲線 | 先盤點既有 TTS，再接受控合成與播放契約 |
| 雲端影片 | 未開始 | 已預留需求，未選擇供應商或資產流程 | 待前述記憶、任務和儲存閉環成熟後再進行 |

## 最優先增補：能力可用性閉環

### 1. 模組巡檢變成艾西可查詢的報告

目前巡檢腳本是良好的第一步，但報告只存在於終端輸出。下一步應由 N1 受控工作者執行唯讀巡檢，將結果寫入固定、非秘密的 JSON 報告，並提供：

| API／任務 | 用途 | 完成證據 |
| --- | --- | --- |
| `POST /api/modules/scan` | 建立一次唯讀掃描任務 | `task_id`、開始時間、掃描範圍 |
| `GET /api/modules/report` | 讀取最近成功報告 | 報告版本、`captured_at`、分類資料、錯誤摘要 |
| `GET /api/modules/:id` | 查詢單一候選模組 | 來源證據、分類、建議與健康檢查 |

艾西可以閱讀與解釋報告，但不能把檔名或舊對話推論為已安裝。報告中的「可用」必須由實際服務狀態和健康檢查共同證明。

### 2. 部署方案與回滾，而非任意命令執行

部署不應接受任意 Shell 指令。每個可部署功能必須先生成一份結構化方案，限定在 N1 的白名單安裝器、固定工作目錄與可驗證健康檢查中。

| 階段 | N1 工作內容 | App／艾西顯示 |
| --- | --- | --- |
| Preflight | 讀取現有模組與相依條件，不讀秘密值 | 衝突、重複候選、磁碟與 GPU 餘裕 |
| Plan | 產生「沿用／補完／合併／新建」計畫 | 變更摘要、影響服務、備份位置、驗收條件 |
| Approval | 主人明確核准指定方案 ID | 等待核准、核准時間與核准人 |
| Deploy | 僅執行白名單腳本與固定參數 | 步驟、日誌摘要、測試與健康檢查 |
| Verify | API、程序、版本與功能測試 | `available`、版本、最後驗證與限制 |
| Rollback | 失敗時回復先前備份或服務版本 | 回滾結果與仍需人工處理項目 |

### 3. 連續對話文件化與跨視窗脈絡

不應用固定聊天總數切斷對話。應在累積到**可設定的內容量門檻**時，把較早段落封存為可追溯文件，保留同一視窗的連續體驗。新視窗開啟時，艾西只讀取與當前題目相關且已成功索引的文件摘要。

每份對話文件至少應保存：來源對話 ID、內容範圍、摘要、決策、目標、未完成待辦、標籤、雜湊、N1 索引狀態、R2 物件鍵（如有）及建立／索引時間。App 必須區分「本機草稿」「等待匯入」「已 N1 索引」「已 R2 封存」四種狀態。

### 4. 常駐工作者、資源門檻與告警

記憶同步、去重、文件摘要、模組掃描與部署驗證都依賴 N1 的常駐工作者。目前 App 能顯示永動腦狀態，但仍需讓工作者有清楚的心跳、佇列、重試、死信、資源門檻和最後失敗原因。這些是「艾西能自主整理」的前提。

建議優先補上：工作者啟動政策、磁碟／GPU 門檻、連續失敗暫停規則、結構化事件日誌，以及 N1 watchdog 的明確保護狀態。背景任務不可因 App 離開前景而中斷。

## 第二優先：角色互動與媒體能力

語音與影片應建立在上述閉環之後。語音先完成「TTS 盤點 → 選擇或新增受權聲線 → N1 合成 → App 播放 → 成功／失敗回報」；語音辨識則採「麥克風 → 受控上傳 → N1 轉寫 → 對話草稿」流程。影片製作最後才接入，並用劇本、分鏡、角色資產、鏡頭、旁白、對嘴、剪輯與 R2 封存做成可替換節點；每個雲端節點均需獨立記錄用量、等待時間與成本。

## 不應優先做的事情

| 項目 | 原因 |
| --- | --- |
| 讓聊天頁直接執行任意命令 | 沒有任務 ID、白名單、測試與回滾，無法知道實際做了什麼 |
| 在 App 內保存 SSH、Git 或雲端密鑰 | 手機不應成為桌機控制權的秘密容器 |
| 把自我回報或聊天文字當作設備／任務證據 | 會讓記憶中心失去可信度 |
| 在記憶同步未跑通前大量丟入影片素材 | 會佔滿本機儲存，且無法證明可被檢索 |
| 先做高成本雲端影片自動化 | 任務、儲存、成本與復原資料鏈尚未成熟 |

## 建議實作順序

1. **模組報告 API 與艾西查詢卡**：使既有盤點報告成為可讀、可追溯的系統事實。
2. **部署方案／核准／健康檢查／回滾**：讓新能力可受控地「真的能用」。
3. **對話分段封存與 N1 索引**：解決新視窗沒有上下文的主要痛點。
4. **記憶同步工作者與告警**：讓長期整理不靠手動操作。
5. **語音輸入與可選 TTS**：在既有模組與資源條件已盤點後部署。
6. **雲端影片工作流與成本帳本**：最後以可替換供應商方式接入。
