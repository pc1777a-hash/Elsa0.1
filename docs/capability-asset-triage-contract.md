# 艾西能力資產盤點與分類契約

本契約的首要目的，是把三機中既有的程式模組、文件、模型、策略素材與半完成工程，轉換為**可驗證、可補完、可索引**的能力候選。清理只在最後處理已驗證沒有能力價值、沒有依賴、已封存且經主人核准的項目。

> 檔案名稱、路徑、安裝器或套件存在，都只是盤點線索；它們不能單獨證明某功能可運作、可被艾西調用，或適合刪除。

| 分類 | 需要的最低證據 | 後續動作 | 是否可自動刪除 |
| --- | --- | --- | --- |
| **可重用候選** | 模組／模型／文件的受控 metadata 與可能能力標籤 | 驗證服務引用、健康端點或最小測試後，建立索引或接線方案 | 否 |
| **可補完候選** | 安裝器、草稿、WIP、待辦或未接線模組線索 | 轉為永動腦任務，寫入依賴、測試、回滾及主人確認點 | 否 |
| **已運作** | PM2、Docker 或 systemd 受管狀態，加上健康契約／最小驗證 | 保留並記錄用途、來源及依賴 | 否 |
| **重複候選** | 同類功能或相同 metadata 指紋，尚未完成呼叫端比較 | 比較入口、依賴、資料來源與呼叫端後才可合併 | 否 |
| **未知** | 僅有路徑或檔名 | 保留並等待人工或受控分析 | 否 |
| **可清理候選** | 無服務引用、無記憶／R2 來源、無模型／系統角色、封存後健康檢查通過 | 先可回復封存，再等待主人核准刪除 | 否，必須核准 |

## 資料最小化與掃描邊界

每個節點的盤點器僅讀取檔案系統 metadata：相對路徑、檔案類型、副檔名、大小、修改時間及推測能力標籤。它不讀取檔案內容，不輸出 `.env`、SSH／雲端金鑰、Token、錢包、Vault、受保護 App 資料、Git 物件、快取或相依套件目錄。大型目錄採用上限掃描；截斷時必須明確回報，不能假裝已完成全量分析。

在有價值候選通過來源允許清單後，才能由 N1 的記憶工作者讀取特定文件的內容、建立摘要與向量索引。該第二階段需要另外的匯入任務、雜湊去重、N1 索引及 R2 封存回報；唯讀巡檢本身不會讓艾西宣稱已學會文件內容。

## 報告與 API

| 項目 | 契約 |
| --- | --- |
| 節點報告檔 | `.elsa_perpetual/capability_inventory/N1.json`、`N2.json`、`N3.json`，由 N1 本機探針按需生成 |
| 節點報告來源 | `elsa-capability-inventory-node/1` |
| App 摘要路由 | `GET /api/system/capability-inventory`，只讀取 N1 已保存的結構化摘要 |
| 節點狀態 | `reported`、`stale`、`probe_failed`、`unreported`，不從 SSH 埠可達性推斷 |
| 能力分類狀態 | `reuse_candidate`、`completion_candidate`、`unknown`；只有外加驗證可升為 `verified_usable` |

## 分析優先順序

1. 先找出現有服務、模型與可重用程式模組，避免重裝同類能力。
2. 接著找出研究文件、操作手冊、策略資料與歷史任務，安排到受控記憶匯入流程。
3. 對半完成安裝器、草稿與未接線模組建立可補完任務，而不是刪除。
4. 最後才分析重複與可清理候選；任何未知項目預設保留。
