# 艾西自我優化治理契約

## 目的

ELSA App 的基礎控制、觀測與任務顯示完成後，艾西可以主動找出能力缺口、舊模組、重複程式與半完成部署，並提出強化自身的方案。自我優化在此代表**受控演進流程**，而不是由模型自行覆寫服務、任意安裝套件或直接改變交易／平台工作者。

> 每次能力變更都必須可追溯至一份唯讀盤點、一份具體提案、一筆主人核准、一次健康檢查與一個可用回滾點。缺少其中任何一項時，狀態應是「待處理」，不是「已優化」。

| 階段 | 艾西可做的事 | N1 必須回報的證據 | App 顯示狀態 |
|---|---|---|---|
| 盤點 | 讀取受控來源中的模組、服務、文件、模型、路由與作業紀錄 | 掃描範圍、時間、清單摘要、雜湊或版本、權限範圍 | 已盤點／盤點過期／未回報 |
| 分析 | 分出可重用、重複、半完成、過期與待研究候選 | 分類理由、相依項、影響範圍、保留／隔離建議 | 草案分析 |
| 提案 | 建立最小變更計畫與驗收條件 | `proposal_id`、檔案／服務清單、預期效果、風險範圍、回滾方法 | 等待核准 |
| 核准 | 由主人核准特定提案與範圍 | `approval_id`、核准時間、有效期限、允許動作 | 已核准／已逾期 |
| 執行 | N1 受控工作者執行已核准步驟 | 任務 ID、開始／結束時間、變更摘要、輸出雜湊 | 執行中／失敗／完成 |
| 驗收與回滾 | 執行健康檢查，必要時回復到已知版本 | 健康檢查報告、回滾點、回滾結果、最終狀態 | 已驗證／已回滾／未回報 |

## 唯讀盤點優先

所有優化都從唯讀盤點開始。N1 的盤點工作者只能收集已白名單路徑、已知服務與不含秘密值的結構化中繼資料；它不得在盤點階段刪檔、改設定、重啟服務、變更交易參數或以「清理」名義移除未知資產。

| 候選分類 | 預設動作 | 是否需要主人核准 |
|---|---|---|
| 已運作且已被參照 | 保留並記錄依賴 | 否，僅更新盤點。 |
| 可重用能力 | 建立接線提案 | 是。 |
| 重複候選 | 提出比較報告與隔離方案 | 是；不得直接刪除。 |
| 半完成模組 | 提出續作、修復或封存提案 | 是。 |
| 無法判定用途的舊資產 | 標為待人工判定，保留原處 | 是，任何移動／刪除均需核准。 |

## 提案格式與最小變更

每份提案必須以最小可回滾變更為單位，不能混合不相干的功能。提案的建議結構如下。

```json
{
  "proposal_id": "proposal-20260818-voice-worker",
  "source_inventory_id": "inventory-20260818-001",
  "title": "接線既有 TTS 工作者",
  "intent": "讓 N1 已驗證的 TTS 工作者提供受控語音輸出",
  "scope": {
    "paths": ["/media/ollama/n1/brain/..."],
    "services": ["elsa-native"],
    "allowed_actions": ["add_route", "restart_named_service"]
  },
  "preflight": ["source_exists", "no_duplicate_active_worker", "syntax_check"],
  "acceptance_checks": ["route_healthcheck", "response_contract", "service_alive"],
  "rollback": { "type": "restore_backup", "reference": "backup-..." },
  "approval_state": "awaiting_approval"
}
```

提案不得包含任何帳密、Token、SSH 私鑰、平台 Cookie 或未經遮罩的設定內容。交易策略、交易平台與多平台工作者還需要各自的風控檔與核准，不得借用一般功能升級的核准範圍。

## 核准、健康檢查與回滾

主人核准應綁定 `proposal_id`、允許動作、範圍與有效期限。N1 只可在有效期內執行提案列出的動作；任何擴大範圍、改變交易參數、跨平台操作或新增外部憑證的需求，都必須產生新提案。完成後，工作者必須先執行提案內的健康檢查，再回報可稽核結果。

若健康檢查失敗，N1 應優先停止新增步驟、保留診斷證據，並依提案內回滾點回復。App 應顯示失敗位置與回滾狀態，而非將「工作者有回應」誤寫成升級成功。

## 後續 App 介面

第一版 App 以「能力地圖」、「待 N1 啟用」與任務生命週期呈現治理資訊。待 N1 安裝受控報告路由後，再新增自我優化看板，讀取提案、核准、執行、健康檢查與回滾報告。未回報資料一律保持獨立的「未回報」狀態，聊天記錄、模型主張或推測不得替代任何治理證據。
